Objetivos y alcance

En un SOC (Security Operations Center), cada alerta de red genera un proceso manual: un técnico recibe la notificación, accede al firewall, ejecuta comandos de diagnóstico, evalúa la gravedad y documenta todo en un ticket. Este proceso consume entre 10 y 15 minutos por incidencia y no aporta valor analítico — es pura fricción operativa.

Este sistema SOAR (Security Orchestration, Automation and Response) se concibe como herramienta interna del N1 que se sitúa entre el momento en que el técnico recibe el ticket en su cola de ServiceNow y el momento en que lo cierra. La solución consume los datos del ticket asignado, consulta automáticamente el firewall FortiOS por API REST, compara el umbral declarado con el valor real, emite un veredicto operativo y genera un ticket enriquecido interno (JSON + texto plano) que el técnico utiliza como apoyo para cerrar el ticket original — en menos de 100 milisegundos. La solución no modifica WOCU ni ServiceNow: opera en paralelo al flujo corporativo.

Caso de uso 1: Caída VPN
Tipo: vpn_down
3 consultas API: estado del túnel, configuración phase1, estado de interfaz
Severidad: siempre CRITICAL
Caso de uso 2: Saturación de recursos
Tipo: resource_saturation
3 consultas API: CPU/memoria, sesiones activas, interfaces
Severidad: CRITICAL / WARNING / INFO según umbrales

El sistema no ejecuta acciones correctivas ni toca WOCU o ServiceNow — su función es automatizar las tareas de comprobación que hoy hace el técnico a mano y entregarle un diagnóstico ya interpretado, liberando su tiempo para el análisis y la toma de decisiones.

Implementación: scripts Python y decisiones de diseño

El sistema lo componen 25 módulos Python (más de 2.000 líneas), organizados en cuatro familias según su función:

FamiliaNºPara qué sirve
Pipeline (núcleo)11Se ejecutan en cadena al llegar una alerta: listener, parser, idempotency, router, severity, output, logger, client/endpoints, vpn, resources
Auxiliares de operación5Arrancar, simular alertas y demostrar: run, simulate_webhook, test_api_connection, demo_severity, demo_live
Scripts de validación3Instrumentación del cap. 6: generate_trial_alerts, measure_triage_time, calculate_impact
Tests648 pruebas (unitarias + integración contra la API real)

Decisiones de diseño justificadas

Flask, no FastAPI
Procesamiento síncrono; simplicidad suficiente para el alcance.
Reglas deterministas, no ML
Auditabilidad: "¿por qué CRITICAL?" siempre tiene respuesta. No hay datos históricos etiquetados.
Idempotencia en memoria
Diccionario con TTL 1h + threading.Lock; sin dependencia de Redis en el prototipo.
Retry con backoff exponencial
Tolerancia a fallos transitorios de la API (timeouts, HTTP 429).

Errores de documentación

Tras la fase de revisión que cierra cada trial manual, llegan al ticket final 2 errores en los 10 trials (1 errata en una IP, 1 omisión de información en el resumen). En la fase de revisión se detectan y corrigen otros 4 errores adicionales que no llegan al ticket final.

El sistema automatizado produce 0 errores en los 10 trials por construcción: los campos copiados se extraen del payload programáticamente y los redactados libremente se generan a partir de los datos reales de la API. Reducción del 100% respecto al proceso manual.

Configuración de la FortiGate VM

La imagen se descarga de support.fortinet.com → Downloads → VM Images → FortiGate (no FortiFirewall) → VMware ESXi → v7.4.11. Se usa el fichero FortiGate-VM64.ovf.

Se importa en VMware Workstation Pro con:

Memoria2 GB (límite de licencia de evaluación)
Procesadores1 (límite de licencia de evaluación)
Network Adapter 1Host-only (gestión — IP 192.168.75.2)
Network Adapter 2NAT (acceso a Internet para licencia)

Tras arrancar (usuario admin, contraseña vacía), se configura el hostname, la IP de gestión en port1, y se obtiene la licencia de evaluación con execute vm-license. La licencia es permanente y no expira.

Se crea un API user soar-reader con perfil api-readonly (sólo lectura) y trusthost limitado a 192.168.75.0/24. El token se genera con execute api-user generate-key soar-reader y se almacena en .env (nunca en el repositorio).

Conclusiones

Los 9 objetivos del TFG se cumplen, y los 4 cuantitativos (O5–O8) se superan con amplio margen: reducción del tiempo de triaje del 99,99%, 100% de campos automatizados, 0 errores de documentación y 100% de acierto del clasificador.

Lecciones aprendidas

  • El diseño desacoplado tiene un retorno tangible: incorporar el segundo caso de uso fue cuestión de un módulo y una línea en el router.
  • Validar contra el sistema real cambia el resultado: detectó incompatibilidades del firmware (HTTP 424, rate limiting) que un mock habría ocultado.
  • Definir indicadores numéricos desde el inicio convirtió la validación en una verificación objetiva, no en una redacción libre.
